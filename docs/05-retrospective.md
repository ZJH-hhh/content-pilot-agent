# 复盘与后续改进

## 最难的问题

难点在于区分「工具运行成功」「方案约束满足」「整个任务完成」三件事。估算出 12 单位本身是成功调用，但对预算 10 的任务仍不可行；保存服务失败时素材和脚本不应被撤销，也不能将保存步骤标为成功。实现中将可行性放入 estimate，将每次执行状态放入 trace，仅在保存工具成功后将任务置为 completed。

第二个难点是重复执行与续跑的语义。重复提交应返回原任务，而续跑才能推进失败任务。使用持久化 requestKey 与显式 resume 接口，将二者区分；续跑加载既有产物，且无法重置累计工具调用上限。

## 当前验证带来的改进

- HTTP 测试揭示 Windows 路径尾分隔符问题，修复规范化后网页可加载。
- 保存工具重新检查当前截止时间，避免将旧的 feasible 估算用于临近截止的任务。
- 成本统计只按最终计划合计，不把多轮评估当成多次实际支出。
- 主题标签排序避免不同主题总使用相同的首个素材。
- 网页续跑检查发现历史轨迹误读最新任务说明，改为每步保存独立摘要，并加入持久化回归断言。
- 将离线策略、模板脚本和真实模型验证边界同时放在页面与文档中，避免演示效果掩盖证据不足。
- 真实模型第一次直接按目录价格选轻量方案，说明原提示没有清楚表达质量优先策略。明确先验证精选方案、再根据实际观察替代后，模型才形成所需预算调整路径；不是由运行器硬编码下一动作。
- 真实请求出现过 45 秒超时，保留未完成结果后增加有界超时配置。最终三场景通过，之前失败与改进过程没有被覆盖。
